# Implementation Plan: Todo In-Memory Python Console App (Phase I)

**Branch**: `001-todo-console-app` | **Date**: 2025-12-25 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-todo-console-app/spec.md`

## Summary

Build a command-line todo application that stores tasks in memory using Python 3.13+. The application provides a menu-driven interface for creating, viewing, updating, completing, and deleting tasks. All data is stored in a Python list and lost when the application exits. This is Phase I of a five-phase evolution toward a cloud-native AI-powered todo system.

**Technical Approach**:
- Python 3.13+ with standard library only (no external dependencies except pytest for testing)
- Dataclass-based Task entity with validation
- List-based in-memory storage with auto-increment IDs
- Function-based menu system with dispatch dictionary
- UTF-8 console I/O with graceful error handling

## Technical Context

**Language/Version**: Python 3.13+
**Primary Dependencies**: Standard library only (dataclasses, datetime, typing); pytest (dev dependency)
**Storage**: In-memory Python list (no persistence)
**Testing**: pytest with unittest.mock for unit and integration tests
**Target Platform**: Cross-platform console application (Windows/WSL 2, Linux, Mac)
**Project Type**: Single project structure (console application)
**Performance Goals**: < 100ms operations for up to 1000 tasks; task creation < 15 seconds
**Constraints**: Standard library only, in-memory storage, no external packages, PEP 8 compliance, max 30 lines per function
**Scale/Scope**: Single-user session, 1000 tasks maximum, 5 core operations (CRUD + toggle)

## Phase 0: Research & Technical Decisions

**Status**: ✅ Completed
**Output**: [research.md](./research.md)

### Decisions Made

1. **Console I/O Pattern**: Standard `input()` and `print()` with UTF-8 encoding
2. **Task Storage**: Python list with dataclass objects
3. **ID Generation**: Auto-increment using `len(tasks) + 1`
4. **Input Validation**: Centralized validation functions with tuple return (is_valid, error_message)
5. **Menu System**: Function-based with dispatch dictionary
6. **Error Handling**: Try-except at boundaries, explicit messages, no stack traces
7. **Display Formatting**: F-strings with manual column alignment
8. **Testing Strategy**: pytest with unittest.mock
9. **Project Structure**: Single project with `src/` and `tests/` directories
10. **Package Management**: UV for project initialization

All "NEEDS CLARIFICATION" items from Technical Context have been resolved. See research.md for detailed rationale and alternatives considered.

## Phase 1: Data Model & Contracts

**Status**: ✅ Completed
**Outputs**: [data-model.md](./data-model.md), [contracts/task_manager_interface.md](./contracts/task_manager_interface.md), [quickstart.md](./quickstart.md)

### Data Model

**Entity: Task**
- **Attributes**: id (int), title (str), description (Optional[str]), completed (bool), created_at (datetime)
- **Validation Rules**: Title 1-200 chars (required), description ≤1000 chars (optional)
- **State Transitions**: pending ↔ completed (toggle), any state → deleted
- **Storage**: Python list with auto-increment ID logic

**Operations**: Create, Read (all/by ID), Update, Toggle Complete, Delete

### Contracts

**TaskManager Interface**:
- `create_task(title, description)` → (Task | None, str)
- `get_all_tasks()` → list[Task]
- `get_task_by_id(task_id)` → Task | None
- `update_task(task_id, title, description)` → (Task | None, str)
- `toggle_complete(task_id)` → (Task | None, str)
- `delete_task(task_id)` → (Task | None, str)

All methods return tuple (result, error_message) for consistent error handling.
